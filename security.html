Security & Incident Response

Last updated: 27 July 2026

Kulova is built and operated by a single founder in Finland. This page describes, honestly and without overstating our size, how we protect data and how we respond if something goes wrong. See also our Privacy Policy.

1. How we protect data day to day

  • All data in transit is encrypted (HTTPS/TLS).
  • Our database (Supabase, EU region) has Row Level Security enabled with a deny-all policy on every table containing merchant or customer data — no client can read or write it directly. Only our backend, using a private service credential, can access it, scoped to the requesting merchant's own store.
  • Production secrets (API keys, database credentials) are stored only in our hosting provider's encrypted environment variable store, never committed to source control.
  • Internal service-to-service calls (e.g. between our backend and the order-lookup endpoint) are authenticated with a private shared secret and are not publicly reachable.
  • Sensitive lookups (like order status) are rate-limited and require an ownership check before returning any data.
  • Every access attempt to protected data fields is logged with a timestamp and session/store identifier, so we can reconstruct what happened during an investigation.

2. Incident response process

As a one-person team, we don't run a 24/7 security operations center — but we do monitor our infrastructure (hosting and database provider dashboards, error logs) regularly, and we act immediately once an issue is identified. Our process:

  1. Detection. An issue is identified — through routine review, an automated alert, a bug report, or a responsible disclosure from a third party.
  2. Containment. Immediate action to stop ongoing exposure: rotating any credential that may be compromised, disabling the affected access path, or taking the affected feature offline if necessary.
  3. Assessment. Determine what happened, what data (if any) could have been accessed, and — critically — whether there is actual evidence of unauthorized access, versus a vulnerability that is closed before being exploited. This determines whether GDPR's breach-notification threshold is met.
  4. Notification. If the assessment concludes that a personal data breach occurred (confirmed unauthorized access, disclosure, or loss of personal data) under GDPR Article 33, we notify the relevant supervisory authority within 72 hours of becoming aware, and notify affected individuals without undue delay where the breach is likely to result in a high risk to their rights and freedoms. If no evidence of actual unauthorized access is found, formal breach notification is not triggered, but we still remediate and document the issue.
  5. Remediation. Fix the root cause, not just the symptom — including related issues discovered during the investigation.
  6. Post-incident review. Document what happened and what changed, so the same class of issue doesn't recur.

3. Worked example: July 2026 credential rotation

What happened

During a routine internal security review, we found a Supabase API key hardcoded in a public-facing page's source code, combined with overly permissive database access policies on several tables. This combination meant the key, if found, could have been used to read or modify stored data directly, bypassing our backend.

What we did, and when

  • Same day: disabled the exposed key and revoked its underlying signing secret, then migrated to newly issued credentials.
  • Same day: assessed for evidence of actual unauthorized access. None was found — the exposure was closed before we found any indication it had been exploited.
  • Following days: rewrote the affected page to route all data access through our authenticated backend instead of talking to the database directly, tightened database access policies table by table (testing after each change), and added additional request-authentication and rate-limiting safeguards.

Why this wasn't formally reported as a breach

Per step 4 of our process above, GDPR's 72-hour notification requirement applies to confirmed personal data breaches. Because we found no evidence of actual unauthorized access before the exposure was closed, this did not meet that threshold. We're including it here anyway, in the interest of transparency, as a real example of this process being followed.

4. Reporting a security issue

If you believe you've found a security vulnerability in Kulova, please email hello@kulova.com with details. We take reports seriously and will respond promptly. Please give us a reasonable time to investigate and fix an issue before disclosing it publicly.
